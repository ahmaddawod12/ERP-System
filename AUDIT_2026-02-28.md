## 1️⃣ ARCHITECTURE REVIEW

### 1.1 System Rule Compliance

**PASS — Core identity rules enforced correctly:**
- `uid` is used consistently for user identity in all Firestore paths.
- `companyId` is server-allocated from `system/data/comid` in `registerBusinessV1` via transaction.
- No email-derived identifiers in paths.
- No `uid` fallback for `companyId`.

**PASS — Inventory is single-document:**
- `companies/{companyId}/data/inventory` with `parts[]` array + `nextId` counter.
- `users/{uid}/data/inventory` same structure for personal inventory.
- `updateInventoryV1` handles all mutations atomically via Firestore transactions.

**PASS — Job model is correct:**
- Single `companies/{companyId}/jobs/{jobId}` collection.
- Plain sequential IDs from `jid` counter (no prefix).
- Status set: `pending`, `waiting`, `finished`, `denied`.

**PASS — Protected writes enforced:**
- Profile: `allow create, update, delete: if false` in rules. All writes via CFs.
- Business info: locked. `updateBusinessInfoV1` handles allowed field updates.
- Jobs: create locked in rules. `createJobV1`, `updateJobV1`, `acceptJobV1`, `deleteJobV1` are the only write paths.
- Inventory: `updateInventoryV1` only write path.

**PASS — No mobile business registration route.**

### 1.2 Violations & Smells

**VIOLATION — `createdByUsername` field in Firestore index:**
- `firestore.indexes.json` line 104 defines a composite index on `documents` collection with field `createdByUsername`. This violates the "no username-derived keys" rule and suggests legacy schema leakage. This field should be `createdBy` (uid-based).
- **Impact:** Dead index burning storage+write cost on every document mutation.

**SMELL — 5,078-line monolith `functions/index.js`:**
- The entire Cloud Functions backend is one file. Contains 30+ exports, helpers, constants, tax authority OAuth, notification triggers, CRUD operations, document generation pipeline.
- Cold start penalty: the entire module graph (axios, @google-cloud/pubsub, firebase-admin, uuid, crypto) loads for every function invocation.
- **Recommendation:** Split into per-domain modules (`auth/`, `jobs/`, `documents/`, `inventory/`, `notifications/`, `tax/`) with a thin `index.js` re-exporting.

**SMELL — Dual region deployment without isolation:**
- `taxAuthorityCallback` and `getInvoiceApproval` are deployed to `me-west1`.
- All other functions are `us-central1`.
- Both share the same codebase, meaning `me-west1` functions load the entire 5K-line module even though they only need tax-related code.

**SMELL — `GenerateTaxInvoice.js` uses `Alert.alert()` directly:**
- Five occurrences of `RNAlert.alert()` in `phone_app/modules/documents/GenerateTaxInvoice.js` bypassing `useAlert()`. This violates the mobile coding instructions and breaks cross-platform alert consistency.

**SMELL — `node-fetch` in `functions/package.json` alongside `axios`:**
- Both `node-fetch` and `axios` are dependencies. Node 22 has native `fetch`. Removing `node-fetch` reduces bundle size.

**SMELL — Every dashboard page is `"use client"`:**
- All 10 pages under `website/src/app/app/` are client components. This makes server-side rendering impossible for the dashboard, increasing bundle size and time-to-interactive.

### 1.3 Duplicated Logic

| Logic | Locations | Risk |
|-------|-----------|------|
| Document ID normalization (`toBaseDocumentId`, `toDocumentDocId`) | `functions/index.js`, `cloudrun-pdf/index.js` | Drift risk — different implementations possible |
| VAT calculation (18% rate) | `functions/index.js` (getInvoiceApproval, publishPreviewTask, publishGenerateTask), `cloudrun-pdf/htmlTemplate.js` | If VAT rate changes, 4+ files need updating |
| Email validation (`isValidEmail`) | `functions/index.js` | Only one location — OK |
| Role normalization | `functions/index.js` | Only one location — OK |
| Invite code generation | `functions/index.js`, `website/src/lib/utils.ts` | Two implementations that could drift |

### 1.4 Scaling Bottlenecks (Architecture-Level)

1. **Company root document contention:** `cid`, `wid`, `jid` counters all live on one document (`companies/{companyId}`). Any concurrent job/client/worker creation serializes on transaction retries for this single document. At 50+ concurrent writes/sec this becomes a bottleneck.

2. **Single inventory document:** With 5,000 parts max and each part having ~6 fields, the document approaches ~200KB. Every single-part mutation rewrites the entire document. No partial array update is possible in Firestore.

3. **Full collection re-fetch on every version bump:** `CacheContext.js` fetches ALL jobs/clients/documents when any version changes. A single job status change triggers fetching the entire jobs collection.

## 2️⃣ FIRESTORE & DATA MODEL OPTIMIZATION

### 2.1 Document Size Risks

**Inventory document (parts[] array):**
- 5,000 parts × ~150 bytes/part = ~750KB. Firestore 1MB limit approached.
- Every `addPart`/`updatePart`/`removePart` rewrites the full document.
- **Risk:** Write amplification. A single part toggle writes 750KB.
- **Mitigation already in place:** 5,000-part cap in `updateInventoryV1`. Acceptable for now.
- **Future:** Consider chunked arrays (e.g., inventory pages of 500 parts each) if approaching limit.

**Job documents with embedded items/photos/signatures:**
- Jobs can contain `parts[]`, `partsUsed[]`, `photos[]`, `signature` (base64?), `images[]`.
- If photos are base64-encoded in the document, a single job could exceed 1MB.
- **Recommendation:** Verify that `photos` and `signature` fields contain Storage URLs, not base64 data.

**Document records with embedded `items[]` and `taxAuthorityResponseData`:**
- Tax invoice documents store the full Tax Authority API response. If the response is large, this adds bloat.
- Items array is uncapped — `MAX_ITEMS_PER_DOCUMENT = 100` is only enforced in Cloud Run, not in `getInvoiceApproval`.

### 2.2 Unbounded Array Concern

- `parts[]` in inventory — capped at 5,000 ✓
- `items[]` in documents — capped at 100 in Cloud Run but **not in `getInvoiceApproval`** ✗
- `partsUsed[]` in jobs — uncapped ✗
- `images[]` in jobs — uncapped ✗
- `tags[]` in jobs — uncapped ✗

**Recommendation:** Add server-side array length validation in `createJobV1` and `getInvoiceApproval`.

### 2.3 Index Analysis

**Active indexes:**
- `jobs`: 5 composite indexes covering status+completedBy+finishedAt, workerId+updatedAt, status+completedBy+createdAt, status+finishedAt, completedBy+createdAt
- `conversations`: 1 index (status+unreadForDev+lastMessageAt)
- `documents`: 1 index (createdByUsername+createdAt) — **uses deprecated field name**

**Missing indexes (likely needed at scale):**
- `jobs` filtered by `status` + `workerId` — workers query their assigned jobs. Current index on `workerId+updatedAt` works, but `status+workerId+createdAt` may be needed for filtered views.
- **No index on `jobs.createdAt` alone** — if any query orders all jobs by creation date without status filter.

**Dead index:**
- `documents` collection index on `createdByUsername` — this field should be `createdBy` (uid). Either the index needs updating or the field needs migration.

**TTL policy:**
- `notificationLog.expireAt` has TTL configured ✓ — good for auto-cleanup.

### 2.4 N+1 and Over-Fetching

**Full collection fetch on cache version change:**
- `CacheContext.js` calls `getDocs(collection('companies/{cid}/jobs'))` with no `limit()` on every `jobsVersion` bump.
- For a company with 10,000 historical jobs, this is 10,000 reads per job mutation.
- **Cost:** At $0.06/100K reads, 100 mutations/day × 10K reads = $6/day per company.

**Sequential re-fetch of multiple collections:**
- When multiple version fields change simultaneously, CacheContext fetches each collection sequentially.
- `Promise.all` would parallelize these fetches.

**Tier 2 (90-180 day) queries:**
- `getDataForMonth` fires a Firestore query for historical data with no result caching between calls.
- Scrolling through document history could trigger repeated identical queries.

### 2.5 Cost Reduction Strategies

1. **Add `updatedAt` filter to re-fetch queries:** Instead of fetching ALL jobs, fetch only `where('updatedAt', '>', lastSyncTimestamp)`. This converts O(N) to O(delta).
2. **Paginate initial load:** On fresh login, fetch first 50 jobs with `limit(50)`, then lazy-load more.
3. **Cache Tier 2 query results in MMKV** with a short TTL (5 minutes) to avoid repeated Firestore reads for the same time range.
4. **Remove dead `createdByUsername` index** — saves write cost on every document creation.

## 3️⃣ SECURITY AUDIT

### 3.1 Strengths

- **App Check enforced globally** via `setGlobalOptions({ enforceAppCheck: true })` ✓
- **Token revocation checking** in `resolveHttpAuth` with `checkRevoked: true` ✓
- **Role resolved server-side** from Firestore profile, never from client payload ✓
- **`validateCompanyId` prevents path traversal** with regex validation ✓
- **Rate limiting** on public endpoints (contactRequestV1, joinCompanyV1, createInviteV1) ✓
- **PII redaction** for email logging ✓
- **Firestore rules deny all client writes** on protected collections ✓
- **CORS origins configurable** via environment variable ✓
- **Worker cannot escalate to manager** — `EDITABLE_ROLES = ['worker', 'user', 'basic']` in `manageWorker` ✓
- **Job field injection prevention** — `ALLOWED_JOB_FIELDS` whitelist in `createJobV1` ✓

### 3.2 Vulnerabilities

**MEDIUM — Client-side `updateDoc` on user cache is allowed:**
- Firestore rules allow users to write to `users/{uid}/data/cache`.
- `CacheContext.js` line 1129 calls `updateDoc(cacheRef, { [field]: FieldValue.increment(1) })`.
- A malicious client could write arbitrary fields to their cache doc (e.g., `role: 'manager'`). However, cache is only used for version tracking, not authorization — so this is **low practical risk**.
- **Recommendation:** Tighten cache rules to only allow incrementing known version fields.

**MEDIUM — Client `update` allowed on `clients` collection:**
- Firestore rule: `allow update: if isAdmin() || isManagerUserBasic(companyId)`.
- Yet `updateClientV1` Cloud Function also exists and validates input.
- This means clients can bypass Cloud Function validation and write arbitrary fields.
- **Recommendation:** Lock client updates to `allow update: if false` and route all writes through `updateClientV1`.

**MEDIUM — Manager/dev can `update` jobs directly via Firestore rules:**
- Rule: `allow update: if isAdmin() || canManageCompany(companyId)` — no field restrictions for managers.
- A manager with raw Firestore access could bypass `updateJobV1` validation (status transitions, field whitelisting).
- **Recommendation:** For maximum safety, lock to `allow update: if false` and enforce all job writes through Cloud Functions.

**LOW — In-memory rate limiter doesn't survive cold starts:**
- `_rateLimitMap` resets on every cold start. A sustained DDoS could exploit this by triggering cold starts.
- **Recommendation:** For production, consider Firebase-based or Redis-based rate limiting. Current implementation is acceptable for moderate traffic.

**LOW — `CORS_ALLOWED_ORIGINS` defaults to empty array in production:**
- If `CORS_ALLOWED_ORIGINS` env var is not set and not in emulator mode, CORS origins default to `[]`.
- Express/Cloud Functions with empty CORS may behave differently than expected.
- **Recommendation:** Fail loudly if CORS origins are empty in production.

**INFO — `contactRequestV1` is exempt from App Check:**
- Intentional for public contact form. Acceptable with IP-based rate limiting in place.

### 3.3 Recommended Rule Tightening

```rules
// BEFORE — client updates bypass validation
match /companies/{companyId}/clients/{clientId} {
  allow update: if isAdmin() || isManagerUserBasic(companyId);
}

// AFTER — all writes through Cloud Functions
match /companies/{companyId}/clients/{clientId} {
  allow read: if isAdmin() || isManagerUserBasic(companyId);
  allow create, update, delete: if false;
}
```

```rules
// BEFORE — manager can update any field on jobs
match /companies/{companyId}/jobs/{jobId} {
  allow update: if isAdmin() || canManageCompany(companyId) || ...;
}

// AFTER — all job writes through Cloud Functions
match /companies/{companyId}/jobs/{jobId} {
  allow read: if ...;  // unchanged
  allow create, update, delete: if false;
}
```

## 4️⃣ MOBILE OPTIMIZATION (Expo 54 / RN 0.81)

### 4.1 Critical Re-render Issues

**`ManageJobs.js` — `React.memo` on `JobCard` is defeated:**
- `handleAcceptJob` and `handleDenyJob` are recreated every render (not wrapped in `useCallback`).
- These are passed as props to `memo`'d `JobCard`, defeating the memo.
- With 100 jobs visible, every state change re-renders all 100 cards.

```javascript
// BEFORE (ManageJobs.js)
const handleAcceptJob = async (jobId) => { ... };
const handleDenyJob = async (jobId) => { ... };

// AFTER
const handleAcceptJob = useCallback(async (jobId) => { ... }, [companyId, acceptJob]);
const handleDenyJob = useCallback(async (jobId) => { ... }, [companyId, updateJob]);
```

**`ManageJobs.js` — Inline `renderItem` in FlatList:**
- `renderItem={({ item }) => <JobCard ... />}` creates a new function every render.
- FlatList's internal optimization is broken.

```javascript
// BEFORE
<FlatList renderItem={({ item }) => <JobCard ... />} />

// AFTER
const renderJobCard = useCallback(({ item }) => (
  <JobCard ... />
), [handleAcceptJob, handleDenyJob, ...]);

<FlatList renderItem={renderJobCard} />
```

**`CreateJob.js` — Zero memoization:**
- No `useMemo`, `useCallback`, or `memo` anywhere.
- Form state changes re-render the entire component including worker list.
- Workers rendered via `.filter().map()` in ScrollView — no virtualization.

### 4.2 Missing Pagination

No screen implements pagination. Every list loads all data into memory:

| Screen | Data | Risk at Scale |
|--------|------|---------------|
| ManageJobs | All company jobs | 10K+ jobs in memory |
| DocumentHistory | All documents | Unbounded |
| ClientBook | All clients | Moderate |
| WorkersUsers | All workers | Low (hundreds max) |
| CompanyInventory | All parts | Capped at 5K |

**Recommendation:** Implement cursor-based pagination with `startAfter()` and `limit(50)` for jobs and documents.

### 4.3 Firestore Listener Optimization

**Good:** Only 2 Firestore listeners per session (user cache + company cache). Listeners pause on background. This is excellent for battery and quota.

**Issue:** `CompanyInventory.js` opens an additional direct `onSnapshot` on `companies/{companyId}/data/inventory`, bypassing the CacheContext pattern. This listener does not benefit from the background pause logic.

**Recommendation:** Move inventory listening into CacheContext for consistent lifecycle management.

### 4.4 Full-Collection Re-fetch

The version-based cache sync strategy fetches entire collections on version bump:

```javascript
// CacheContext.js — triggered on every jobsVersion change
const jobsSnap = await getDocs(collection(db, `companies/${companyId}/jobs`));
```

**This is the single biggest performance+cost issue in the app.** At 10K jobs, a single job creation triggers 10K document reads.

**Fix:** Add incremental sync:
```javascript
// Incremental: only fetch jobs updated since last sync
const q = query(
  collection(db, `companies/${companyId}/jobs`),
  where('updatedAt', '>', lastSyncTimestamp),
  orderBy('updatedAt', 'desc')
);
const newJobsSnap = await getDocs(q);
// Merge into existing cache
```

### 4.5 Sequential Fetches Should Be Parallel

```javascript
// BEFORE — CacheContext.js version sync handler
if (jobsVersionChanged) await fetchAllRecentJobs();
if (docsVersionChanged) await fetchAllDocuments();
if (clientsVersionChanged) await fetchAllClients();
if (workersVersionChanged) await fetchAllWorkers();

// AFTER
const fetches = [];
if (jobsVersionChanged) fetches.push(fetchAllRecentJobs());
if (docsVersionChanged) fetches.push(fetchAllDocuments());
if (clientsVersionChanged) fetches.push(fetchAllClients());
if (workersVersionChanged) fetches.push(fetchAllWorkers());
await Promise.all(fetches);
```

### 4.6 `GenerateTaxInvoice.js` — 2,573 Lines

This is an extremely large component that should be split:
- Tax Authority submission logic → dedicated hook (`useTaxInvoiceSubmission`)
- Job selection UI → sub-component
- Item management UI → sub-component
- Client selection UI → sub-component (already uses `ClientSelector`)
- Preview logic → sub-component

## 5️⃣ NEXT.JS 16 OPTIMIZATION

### 5.1 Every Dashboard Page is a Client Component

All 10 pages under `/app/app/` have `"use client"` at line 1. This means:
- No server-side data fetching
- Full React hydration cost on every page load
- No streaming/suspense benefits
- Component JS shipped entirely to client

**Why this happened:** These pages use hooks (`useAuth`, `useEffect`, `useState`) for Firebase client SDK data fetching.

**Recommended pattern:** Split into server component wrapper + client interactive shell:

```tsx
// app/app/jobs/page.tsx (server component — NO "use client")
import { Suspense } from "react";
import JobsClient from "./jobs-client";
import { LoadingState } from "@/components/states/loading-state";

export default function JobsPage() {
  return (
    <Suspense fallback={<LoadingState />}>
      <JobsClient />
    </Suspense>
  );
}

// app/app/jobs/jobs-client.tsx ("use client")
export default function JobsClient() {
  // ... existing client logic
}
```

This enables route-level code splitting and loading UI via React Suspense.

### 5.2 Missing `loading.tsx` Segment Files

No route segment has a `loading.tsx` file. Adding these provides instant loading UI during route transitions:

```tsx
// app/app/loading.tsx
export default function DashboardLoading() {
  return <LoadingState message="Loading..." />;
}
```

### 5.3 Missing Middleware

No `middleware.ts` exists. Server-side auth checking happens in individual API routes. Adding middleware would:
- Centralize auth redirect logic (unauthenticated → `/login`)
- Reduce client-side auth-check flash
- Protect all `/app/*` routes uniformly

```typescript
// middleware.ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  const token = request.cookies.get("__session")?.value;
  if (!token && request.nextUrl.pathname.startsWith("/app")) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  return NextResponse.next();
}

export const config = {
  matcher: ["/app/:path*"],
};
```

### 5.4 Caching Gaps

- No `Cache-Control` headers on API routes (except `taxAuthorityCallback`).
- No `revalidate` on any server component.
- Static marketing pages (`/features`, `/pricing`, `/security`, etc.) are not explicitly cached.
- **Recommendation:** Add `export const revalidate = 3600` to static pages.

### 5.5 `useEffect` for Data Fetching

Dashboard pages use `useEffect` → `firestoreService.listX()` pattern. This is the pre-React 19 pattern. With Next.js 16 + React 19:
- Consider `use()` hook for promise unwrapping
- Consider server-side data fetching where Firebase Admin SDK is available

## 6️⃣ CLOUD FUNCTIONS OPTIMIZATION (Node 22 / v7)

### 6.1 Non-Transactional Critical Operations

**`manageWorker` add action — Auth creation outside transaction:**
- The Firebase Auth user is created (`admin.auth().createUser()`) before the Firestore batch.
- If the batch fails, an orphaned Auth user exists with no Firestore data.
- **Recommendation:** If Auth creation fails, catch and clean up. If Firestore batch fails after Auth creation, delete the Auth user in a catch block.

**`manageWorker` delete action — Sequential non-atomic operations:**
- Auth user deleted → user data deleted → worker doc deleted → jobs cleaned up → cache bumped.
- If any step fails, partial deletion occurs.
- **Recommendation:** Tolerate partial failure (already does with try/catch on cleanup). Consider queuing cleanup via Pub/Sub for retry.

**`getInvoiceApproval` — Document saved outside the counter transaction:**
- Tax Authority API call between counter transaction and document save.
- If API succeeds but Firestore save fails, the document number is consumed but no document exists.
- Already addressed with good error handling but worth noting.

### 6.2 Cold Start Optimization

- **5,078 lines in one file** — every function loads the full module.
- deps: `firebase-admin`, `@google-cloud/pubsub`, `axios`, `axios-retry`, `node-fetch`, `uuid`, `crypto`.
- **`setInterval` for rate limit cleanup** runs on every instance — minor but unnecessary overhead for most functions.

**Recommendation:** Split into per-function entry points or use dynamic `require()` for heavy deps:

```javascript
// Only load PubSub when needed
let _pubsub;
function getPubSub() {
  if (!_pubsub) _pubsub = new (require("@google-cloud/pubsub").PubSub)();
  return _pubsub;
}
```

### 6.3 Missing Idempotency

- `createJobV1` — Creating the same job twice (retry) increments `jid` twice. Cloud Functions v2 has at-least-once delivery.
- **Recommendation:** Accept an optional client-generated `idempotencyKey`. Before incrementing counter, check if a job with that key already exists.

- `getInvoiceApproval` — Retry scenarios could submit the same invoice twice to Tax Authority.
- Partially mitigated by the document number transaction, but Tax Authority may see duplicate submissions.

### 6.4 Error Handling Gaps

- `saveAuditLog` silently swallows errors. If audit logging is compliance-critical, this should be more visible.
- `recursiveDelete` can be extremely slow for large subcollection trees. Consider `firebase-tools` `firestore:delete` or batched deletes.

### 6.5 Over-Fetching in `assertHttpCompanyAccess`

- Every call reads **both** the user profile AND the worker membership doc.
- For functions that already have the profile (e.g., `getAuthenticatedUserProfile` called first), this is redundant.
- **Recommendation:** Accept optional pre-loaded profile to avoid double reads.

### 6.6 `maxInstances: 10` Is Very Conservative

- With 10 max instances and all functions sharing the same deployment, a spike in one function starves others.
- Tax Authority callback has its own region (`me-west1`) which helps isolation.
- **Recommendation:** Set per-function `maxInstances` for critical paths (`getInvoiceApproval: 5`, `onJobAssignTrigger: 3`, etc.) and raise the global to at least 25.

## 7️⃣ SCALABILITY RISK FORECAST

### 100 Companies

**Works fine.** Current architecture handles this well.

Potential issues:
- `system/data/comid` document has minimal contention (registrations are infrequent).
- Firestore read volume stays manageable.

### 1,000 Companies

**Stress points emerge:**

1. **Full collection re-fetch cost:** If average company has 500 jobs and 20 mutations/day:
   - 1,000 × 20 × 500 = **10M reads/day** just from cache sync.
   - Cost: ~$6/day = ~$180/month from cache sync alone.

2. **Cloud Functions cold starts:** With mixed regions and 10 max instances, peak traffic may cause queuing.

3. **Cloud Run PDF service (max 5 instances, concurrency 2):**
   - Max throughput: 10 concurrent PDFs.
   - If 100 companies generate invoices simultaneously during end-of-month billing: queue backup.

### 10,000 Companies

**Architectural limits hit:**

1. **Firestore reads explode:**
   - 10K companies × 1K jobs avg × 50 mutations/day = **500M reads/day**.
   - Cost: ~$300/day = **$9,000/month** just from cache sync.
   - **Fix required:** Incremental sync is mandatory at this scale.

2. **Company root document contention:**
   - Large companies with 50+ workers creating jobs simultaneously.
   - `jid` counter on single document = 1 write/sec limit per company (Firestore sustained write rate).
   - **Fix:** Distributed counters (shard the counter across N documents, merge on read).

3. **Inventory single-document write contention:**
   - Multiple workers picking parts simultaneously.
   - Transaction retries increase with concurrent writers.
   - At 10+ concurrent picks: transaction failure rate increases.
   - **Fix:** Consider per-part documents or sharded inventory segments.

4. **Pub/Sub PDF queue:**
   - End-of-month invoice burst: thousands of PDF requests.
   - Cloud Run scale-up latency + Puppeteer memory usage (~500MB/instance).
   - **Fix:** Pre-warm Cloud Run instances, increase max instances.

5. **`notificationLog` collection grows unbounded:**
   - TTL is 30 days but collection scan for deduplication reads a document per notification.
   - At 10K companies sending multiple notifications/day: millions of docs/month.
   - TTL cleanup handles this, but write volume during peak is high.

### Firestore Limits Hit First

| Limit | Threshold | When |
|-------|-----------|------|
| 1 write/sec on single document | Company counter (`jid`/`cid`/`wid`) | ~50 concurrent job creates |
| 1MB document size | Inventory with 5,000+ large parts | ~4,000–5,000 parts with descriptions |
| 10MB/sec write throughput per database | Across all companies | ~50K active companies |
| 500 composite indexes | 7 currently used | Very far off |

### 9.1 Improved CacheContext Incremental Sync

```javascript
// BEFORE — Full collection re-fetch
const fetchAllRecentJobs = async () => {
  const jobsRef = collection(db, `companies/${companyId}/jobs`);
  const snap = await getDocs(jobsRef);
  const allJobs = snap.docs.map(d => ({ id: d.id, ...d.data() }));
  setJobs(allJobs);
  saveToLocalCache(CACHE_KEYS.JOBS, allJobs);
};

// AFTER — Incremental sync with merge
const syncJobsDelta = async () => {
  const lastSync = getFromLocalCache('jobsLastSync') || '1970-01-01T00:00:00Z';
  const jobsRef = collection(db, `companies/${companyId}/jobs`);
  const q = query(
    jobsRef,
    where('updatedAt', '>', lastSync),
    orderBy('updatedAt', 'desc'),
    limit(500) // Safety cap
  );
  const snap = await getDocs(q);
  if (snap.empty) return; // No changes

  const updates = snap.docs.map(d => ({ id: d.id, ...d.data() }));
  const now = new Date().toISOString();

  setJobs(prev => {
    const merged = [...prev];
    for (const updated of updates) {
      const idx = merged.findIndex(j => j.id === updated.id);
      if (idx >= 0) merged[idx] = updated;
      else merged.push(updated);
    }
    saveToLocalCache(CACHE_KEYS.JOBS, merged);
    saveToLocalCache('jobsLastSync', now);
    return merged;
  });
};
```

### 9.2 Improved Firestore Transaction Pattern

```javascript
// BEFORE — Auth user created outside transaction (manageWorker add)
const userRecord = await admin.auth().createUser({ ... });
const batch = admin.firestore().batch();
batch.set(profileRef, { ... });
batch.set(workerRef, { ... });

// If batch fails, orphaned Auth user exists!

// AFTER — With cleanup on failure
let userRecord;
try {
  // Step 1: Create Auth user
  userRecord = await admin.auth().createUser({ ... });

  // Step 2: Firestore writes (inside transaction for counter)
  await admin.firestore().runTransaction(async (tx) => {
    const companySnap = await tx.get(companyRef);
    const wid = Number(companySnap.data()?.wid || 1);
    tx.set(companyRef, { wid: wid + 1 }, { merge: true });
    tx.set(profileRef, { uid: userRecord.uid, wid, ... });
    tx.set(workerRef, { uid: userRecord.uid, wid, ... });
    tx.set(cacheRef, { ... });
  });
} catch (error) {
  // Cleanup orphaned Auth user
  if (userRecord?.uid) {
    try { await admin.auth().deleteUser(userRecord.uid); }
    catch (cleanupErr) { logger.error('Orphan cleanup failed', { uid: userRecord.uid }); }
  }
  throw error;
}
```
